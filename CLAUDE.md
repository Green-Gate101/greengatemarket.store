# CLAUDE.md — Green Gate Marketplace

Guidance for AI coding agents (Claude Code and friends) working on this repository.

## What this is

**Green Gate Marketplace** (greengatemarket.store) — a production South-African
marketplace (Amazon/Takealot model): buyers check out in-app, sellers own stores,
the marketplace is merchant-of-record for in-app card payments and pays sellers
out automatically less a 5% platform fee.

Two apps live in this repository:

| App | Location | Domain | Deployment |
|---|---|---|---|
| Storefront + API | repo root (`src/`) | greengatemarket.store | Vercel project, Git-connected to `Green-Gate101/greengatemarket.store` (main) |
| Admin console | `admin-console/` | admin.greengatemarket.store | Vercel project `greengate-admin-console`, Git-connected to its own repo `Green-Gate101/greengate-admin-console` (the subtree is pushed there), manual fallback: `VERCEL_TOKEN=… node scripts/deploy-admin-rest.mjs` |

## Stack & commands

- Next.js 16 (App Router) + TypeScript 5 + React 19, Tailwind 4 + shadcn/ui (New York), Prisma 6 (**SQLite locally, hosted Postgres in production**), NextAuth v4 (credentials + Google), sharp, zod.
- **Storefront**: `bun run dev` (port 3000, logs tee to `dev.log`), `bun run lint`, `bunx tsc --noEmit`, `bun run db:push` (schema in `prisma/schema.prisma`, local DB file `db/custom.db`).
- **Admin console**: own `package.json` — run `bun install` inside `admin-console/` first; then `bunx tsc --noEmit` there. It is a thin server-side auth proxy: it never talks to the DB, it proxies to the marketplace admin API with a parked session cookie.
- Prisma client is generated for SQLite locally. **Production runs on hosted Postgres**: on Vercel `scripts/prepare-db.sh` pushes `prisma/schema.postgres.prisma` (no data loss allowed) and generates the Postgres client; a PRODUCTION build with no working hosted database now FAILS on purpose (the live deployment stays) instead of going live on an ephemeral SQLite file. Keep both schema files in step. If a fresh local process can't find tables, run `bunx prisma generate` then `bun run db:push`.
- Human-oriented internal docs live in `docs/` (architecture, payments, delivery, images, operations, devices, testing, scale) — update them with any change to those areas.

## Architecture facts that will bite you if ignored

1. **The user-visible site is a single route (`src/app/page.tsx`) with hash-based SPA routing** (`#/product/<slug>`, `#/dashboard`, …) driven by `useSyncExternalStore` in `src/components/greengate/app-shell.tsx`. Do not introduce new Next.js routes for screens; extend `parseHash` + the view map. Components live in `src/components/greengate/`. **The one exception is crawlable landing pages** (owner-requested, for SEO + WhatsApp/Facebook link previews): `src/app/product/[slug]` and `src/app/store/[slug]` server-render metadata, Open Graph and schema.org JSON-LD from `src/lib/seo.ts`, then hand over to the SPA via `SpaLanding` (sets `#/product/<slug>` / `#/store/<slug>` when no hash is present). AppShell `replaceState`s the address bar to `/product/<slug>` / `/store/<slug>` while those views are open and back to `/` otherwise, so copied links always preview. Photos for bots come from `/api/images/<imageId>` and `/api/images/store/<storeId>` (base64 → binary, edge-cached). `sitemap.ts` lists every active store and approved product (≤50k URLs).
2. **Never trust the client.** All pricing is recomputed server-side from the DB; roles are re-verified from the DB on every privileged call (`requireUser` / `requireRole` in `src/lib/auth.ts`); images are validated by magic bytes; product photos pass the AI guard (`src/lib/ai-image-guard.ts`) and the white-background studio pipeline (`src/lib/image-processing.ts` — flood-fill background removal, then composite on a white square canvas; it never fails a listing: on any processing error the normalised original ships).
3. **Money is integer cents everywhere** (`priceCents`, `totalCents = subtotalCents + shippingCents`). Fee math: `Math.round((gross * pct) / 100)`. **Shipping is quoted PER STORE** at checkout (each seller's own origin + parcels; a multi-seller cart charges each order its own leg — never the first store's rate). Every outbound fetch has a hard timeout: Algolia 4s (search falls back to the DB on failure/empty), Resend 12s, Yoco 12s, Courier Guy 6.5s, geocoders 5–6s — keep it that way; nothing external may hang a request path.
4. **All payment paths funnel through `settleOrderPayment()` in `src/lib/ggpay.ts`** — the single choke-point that marks an order paid (atomic conditional `updateMany` claim; cancelled/refunded orders can never be settled). Marketplace rails (GGPay card, marketplace PayFast, bank transfer) queue a Payout (gross − 5% fee). **Seller-owned rails (`payfast_seller`, `ozow`) must NOT queue a payout** — the money already went to the seller's own gateway account (same for seller-owned Yoco, which has its own confirm path in `src/lib/yoco.ts`).
5. **In-app GGPay engine mode**: `ggpayEngineMode()` is `test` without `GGPAY_ACQUIRER_KEY` (sandbox cards only; real cards refused honestly) and `live` with it — but `live` **hard-refuses every charge** until the production routing hook in `chargeCard()` (src/lib/ggpay.ts) actually wires an acquirer. A credential alone never moves money; nothing may ever "approve" a card without a real charge. Do not remove this guard. **Deployed sandbox guard**: sandbox approvals settle orders only where `ggpaySandboxAllowed()` is true — local dev (`NODE_ENV !== 'production'`) or an isolated test deployment with its own database that sets `GGPAY_ALLOW_SANDBOX=1`. Every Vercel build (production AND preview, which share the production DB) refuses all cards, and `payments.ggpay` (from `/api/checkout`, `/api/orders`, `/api/orders/[id]`) hides the card form. Before this guard the public `4242` card marked real orders paid and queued real payouts.
6. **Webhook binding rules (do not weaken)**: PayFast seller-mode ITN must match BOTH the seller's passphrase signature AND `merchant_id` AND `order.storeId === store.id`; Ozow notify stamps `ozowTransactionId` only AFTER positive proof; Yoco webhook/return only trust the checkout id stored on the order (never the payload's) and require the retrieved checkout's `amountCents === order.totalCents` (fail closed when Yoco reports no amount).
7. **Only ACTIVE stores sell**: catalogue, product detail, recommendations, cart, wishlist and checkout all filter `store.status === 'active'`. Admin moderation stands — a seller cannot re-approve a product that has a `moderationNote`.
8. **Multi-store checkout partial failure**: stores processed before a stock conflict keep their orders; the 201 response carries `partialFailure` so the buyer is told honestly what succeeded. The in-app cart/checkout lives in `#/account` (AccountView `initialTab="checkout"`; `#/checkout` is NOT a route — it falls back to the home page) — there is NO `/checkout/pay` route; recovery links point to `/#/orders`.
9. **Secrets** (seller PayFast/Ozow/Yoco keys) are AES-256-GCM encrypted (`src/lib/secret-box.ts`, key derived from `NEXTAUTH_SECRET` — fails closed in production if unset) and are write-only through the API.
10. Rate limiting is in-process (`src/lib/rate-limit.ts`) — acceptable for single-instance; don't rely on it across instances. Credentials login is limited 10/15min per email+IP inside `authorize` (locked-out attackers see the generic wrong-password response). Public webhooks (PayFast ITN, Ozow notify, Yoco webhook/return) each carry a per-IP ceiling.
11. **Always-on monitor**: `/api/cron/system-watch` (Vercel Cron — scheduled daily in `vercel.json` because the team is on the Hobby plan, which only executes crons once/day; for around-the-clock coverage point an external pinger (UptimeRobot / cron-job.org) at the URL every minute with `Authorization: Bearer <CRON_SECRET>`, or upgrade to Pro and set the schedule to `* * * * *`) runs deep checks (db latency, stuck payment claims, rails posture, live Algolia probe every 5th run, email/Google drift), opens/closes `MonitorIncident` rows, and emails `ADMIN_EMAIL` exactly once per incident + once on recovery (`sendSystemAlertEmail`). `/api/monitor` (admin-only) runs the same incident machine on every pull and surfaces checks + incidents; the admin console's **System monitor** tab polls it every second. Do not remove the cron when testing — it is the uptime record.
12. **Payout hold**: a payout whose order is `cancelled`, `refunded` or `returned` is ON HOLD (`payoutOnHold` / `PAYOUT_HOLD_ORDER_STATUSES` in `src/lib/payments.ts`) — both `/api/payouts` PATCH and the admin `payout_status` action refuse to move it (409), payout lists carry `held` + `orderStatus`, and summaries report `held` so "owed" excludes it. The buyer must be refunded instead. Never pay out a held payout.
13. **Password reset signs out every other session**: the JWT carries `pwf` (`passwordFingerprint` of the password hash, `src/lib/auth.ts`); `requireUser` refuses a session whose fingerprint no longer matches (401 "Your password was changed") and `/api/auth/me` answers `sessionExpired: true` so the header signs the browser out. Sessions issued before this existed (no `pwf`) pass until they expire (7 days). Never rewrite `passwordHash` outside register/reset/first admin seed, or every device signs out.
14. **Financial records are forever**: `admin delete_user` AND `admin delete_order` refuse (409) when money trails are involved (paid orders; delete_order also cannot destroy a paid order's Payment/Payout cascade) — suspend (ban) instead. `confirm_payment` is an atomic guarded `updateMany` claim — concurrent confirms cannot double-fire. Admin POST carries a 120/min per-admin burst limit.

## Environment variables (Vercel production)

`DATABASE_URL`, `NEXTAUTH_SECRET` (required — secret-box and sessions fail closed without it), `ADMIN_EMAIL`, `ADMIN_PASSWORD` (seeds the administrator's FIRST password only — it is never re-applied over an existing one, so "Forgot password" resets stick), `CRON_SECRET` (authenticates Vercel Cron → `/api/cron/*`; set it or the recovery/system-watch routes stay open). Optional integrations: `ALGOLIA_*`, `RESEND_API_KEY`/`RESEND_FROM`, `COURIER_GUY_API_KEY`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `PAYFAST_MERCHANT_ID`/`PAYFAST_MERCHANT_KEY`/`PAYFAST_PASSPHRASE` (all three required for the marketplace PayFast rail), `PAYFAST_SANDBOX=1`, `OZOW_IS_TEST` (production defaults to LIVE; dev/preview default to test), `GGPAY_ACQUIRER_KEY` (present ⇒ live mode; charges stay refused until the acquirer hook is wired — see fact 5), `GG_PLATFORM_FEE_PERCENT` (default 5).

## Scale path (10M buyers/sellers) — see docs/scale.md
The data model carries hot-path composites (`[status, createdAt]`, `[status, categoryId]`, plus Order `yocoCheckoutId`, `[status, paymentStatus, createdAt]`, OrderItem `productId`, Store `status`, ProductEvent `[type, createdAt]`) and `prisma/schema.postgres.prisma` mirrors every index. Production runs on hosted Postgres (Supabase, pooled) with the shared limiter on Upstash Redis. Rules that keep it standing under heavy traffic:
- **Never `+1` a shared row per request.** Counters many visitors bump (view counts, API-usage tallies) go through `addToCounter` (`src/lib/batched-counter.ts`). The recommender's shared model changes go through its own batch (`changeModel` in `src/lib/recommender.ts`) — never `saveJSON('model', …)` per event.
- **Never hand out a shared default object to be mutated.** `loadJSON` returns a fresh copy of the fallback (the shared empty profile used to leak one new visitor's browsing into the next one's "personalised" picks).
- **Public answers the same for everyone carry an edge-cache header** (`public, s-maxage=…, stale-while-revalidate=…`); anything that reads the session must not. A shopper who just changed something reloads past the cache (the product page adds `?fresh=` after a review).
- **Small slots use small photos**: `sizedImage(src, width)` → `/api/images/<id>?w=…`.
- Interactive transactions on money paths pass `{ maxWait: 10_000, timeout: 20_000 }`.
- **Product events are kept for 180 days** (`PRODUCT_EVENT_KEEP_DAYS`, `src/lib/retention.ts`), pruned by the daily `abandoned-checkouts` cron with the time left after its other jobs (Hobby allows two crons — never add a third). A new event type must be added to `EVENT_TYPES` there or it is never pruned. Anything that must last forever does not belong in `ProductEvent`.
- Per-IP limits must allow for carrier NAT (many shoppers share one IP); keep strict limits per email/account.

## House rules (project owner's standing directives)

- **English only**, everywhere, always.
- **Never break working code; additive changes only.** No rewrites of functioning systems.
- **Nothing fake**: no seeded/fake data, no fake payment approvals, honest error messages (a rejected card is a rejected card; a sandbox charge is disclosed as sandbox).
- No second-hand clothing/footwear listings; no replicas/counterfeits.
- Every change ships to **both apps in lockstep**: commit → push GitHub main (storefront) → push the `admin-console/` subtree to its repo (or REST-deploy it) → verify BOTH domains serve the new build.
- **Every screen must fit a 320px-wide phone with no sideways scroll** (iPhone SE 1st gen / small Androids — verified across WebKit, Chromium and Firefox). Long button labels wrap (`h-auto min-h-11 whitespace-normal`, as on the seller pay buttons); the header tightens its spacing below `sm` because a signed-in header (bell + theme + account + cart) used to overflow by 2px. Feature-detect browser APIs with `typeof X === 'undefined'` (IntersectionObserver, ResizeObserver, crypto.randomUUID — the guest id falls back to getRandomValues/Math.random).
- The cookie banner (`CookieConsent`) is position-fixed; `ConsentBottomSpacer` (same file, mounted in app-shell before `<Footer />`) reserves its measured height in the page flow while consent is undecided so fixed-banner overlays can never make bottom CTAs unreachable (this bug silently blocked checkout Place-order taps). Keep the spacer if the banner stays fixed.
- Store logo/banner uploads are normalized through sharp before storage and flattened onto WHITE (application: ≤1280px JPEG q85; store profile `POST /api/sellers/branding`: logo ≤512px JPEG q90 4:4:4, banner ≤1600px JPEG q85, see `src/lib/store-images.ts`). Sellers change them any time in the dashboard **Store profile** card. Public addresses carry `?v=<storeImageVersion>` so the day-long edge cache never shows an old logo; the store page shows the whole logo (`object-contain`). The public sellers directory must never ship base64 rows.
- `worklog.md` and `.env` are git-ignored; never commit tokens.
- Check `dev.log` (tail) for runtime errors after changes; lint + `tsc --noEmit` on BOTH apps before any deploy.

## E2E testing patterns that work here

- NextAuth credentials flow with cookie jars: GET `/api/auth/csrf` → POST `/api/auth/callback/credentials` (form-urlencoded). See `scripts/e2e-seller-flow.mjs` for the working harness (jars, multipart, the full seller questionnaire field list).
- GGPay sandbox test card (LOCAL dev only — refused on every Vercel deployment, see fact 5): `4242424242424242`, any future `MM/YY`, any 3-digit CVV. Declines: tail `0002` (bank decline), `9995` (insufficient funds), `0069` (fraud flag).
- Emails: every user-supplied value (names, store/product names, seller notes) goes through `escapeHtml()` from `src/lib/email.ts` — HTML built by callers (e.g. checkout `itemsText`) must escape too.
- Order numbers are `GG-` + 8 CSPRNG chars; checkout retries on a `number` unique-constraint collision (`withFreshOrderNumber`).
- Ozow hashes: the concatenated string is lowercased before SHA-512 (Ozow's documented recipe); compare with `ozowHashMatches`.
- **Sellers edit live listings** in "Your listings" (`EditListing` in `sell-view.tsx`): price, sale price and stock, or stock per size. `PATCH /api/products/<id>` accepts `variants: [{ id, stock }]` (only that product's own sizes are touched, 0–1,000,000) and ends a sale automatically when the new price is at or below the sale price. `GET /api/seller/products` returns each size with a readable `label`.
- **Two-column grids use `[&>*]:min-w-0`** so a long product name can never stretch a column past the screen (the seller "List a product" page was 518px wide on phones before). Keep it on any new `lg:grid-cols-[…]` layout.
- **A failed load must never look like "empty"**: queries throw on `!res.ok` and screens show "We could not load … — Try again". Before, one failed `/api/sellers?mine=1` showed existing sellers "You need a store first / Create my store", and failed listings/wishlist loads read as "No products yet" / "Your wishlist is empty".
- Client screens read API answers with `readJson(res)` (`src/lib/utils.ts`) or `res.json().catch(() => ({}))` for error text — never a bare `res.json()`, which showed buyers "Unexpected token '<'" when the host returned an HTML error page (or a public Wi-Fi login page answered 200 with HTML). Every screen now does; keep it that way.
- **Routes read JSON bodies with `readJsonObject(req)`** (`src/lib/request-body.ts`) and answer `invalidJsonBody()` (400) when it returns null — broken JSON, `null`, a list or a bare value used to answer 500 on 24 routes. Never `await req.json()` unguarded. Test: `qa/bad-body-probe.mjs`.
- **Signed-in changes share a per-account ceiling**: cart, wishlist, notifications, saved addresses, profile, listing edit/delete and seller order updates call ``rateLimit(`account-writes:${userId}`, 300, 60_000)`` right after the session check (no person comes close; it stops scripted floods).
- **Products with sizes keep `stock = 0` on the product row** — stock lives on each active variant. Every list payload (`/api/products`, `/api/recommendations`, `/api/wishlist`) carries `variantStock` + `hasVariants`; cards treat `stock + variantStock` as availability and their button reads "Choose" (opens the product page to pick a size — the cart refuses a variant product without one). Seller analytics count low/out-of-stock from the sizes too. Never judge availability from `product.stock` alone.
- Catalogue (`/api/products`) and recommendations return `image` as `/api/images/<imageId>` (edge-cached file), NOT the base64 data URL — keep public list payloads small. Detail/cart/seller views still carry data URLs (they include non-public products the image endpoint will not serve).
- `/api/payments/payfast/start?number=` builds the signed marketplace PayFast redirect (the order views link to it when `payments.payfast` is on); success is still decided only by the ITN.
- Changing payout bank details (`PATCH /api/sellers`) always notifies the owner in-app + by email (`sendPayoutDetailsChangedEmail`) — payout redirection is the classic takeover move.

## Seller subscriptions (owner's rule) — see docs/subscriptions.md

- R499/month or R6 999/year (env-overridable), paid on Green Gate's own Yoco (`YOCO_PLATFORM_SECRET_KEY`); 30-day trial once, started on approval (`store_status` → `trialStartData()`), existing stores backfilled at bootstrap. Free: admin-owned stores + admin-granted `billingExempt`.
- `Store.accessUntil` (max of trial / paid) is the selling switch: EVERY buyer-facing query uses `sellingStoreWhere()` / `storeCanSell()` (catalogue, search, suggest, directory, store page, product page, recommendations, cart, wishlist, reviews, checkout, images, sitemap, SEO pages). New buyer-facing code MUST use them too — never `store.status === 'active'` alone.
- Lapsed sellers: tools locked with 402 via `requireSellerTools` (listings, store profile, payment settings, analytics); orders, payouts, messages and billing stay open.
- A payment counts only after `verifySubscriptionPayment` retrieves the stored checkout from Yoco with the exact amount; `settleSubscriptionPayment` is an atomic claim. Housekeeping rides on the abandoned-checkouts cron (Hobby = 2 crons max — do NOT add a third).
- Admin ↔ seller messages: `SellerMessage`, plain text (`cleanMessageText`), seller `/api/seller/messages`, admin actions `send_seller_message` / `mark_seller_messages_read` / `billing_exempt` (console tabs Subscriptions + Messages; the Messages tab re-reads every 15 s; `#messages` in the console address opens it — the admin's "Message from <store>" bell link, absolute https links open in a new tab).
- Is it on? `subscriptionPaymentsStatus()` (key set + `sk_live_` + Yoco accepts it, cached 10 min) feeds `/api/health`, the System monitor and the console's Subscriptions tab. Crediting is race-safe across two payments of one store (`accessUntil` moves only from the value read); stale checkouts are closed only after a last Yoco check.
- Header search suggestions: `search-suggest.tsx` + `/api/search/suggest` (only the arrow keys choose what Enter opens; mouse hover never does). The list keeps the last suggestions while the next ones load (no blinking while typing) and shows "Search for …" from the first letter; when Algolia's hits are all non-live the DB answers; popular searches only show plain words (no links/emails).

## Seller applications

- The six-step form (`StoreOnboarding` in `sell-view.tsx`) posts multipart to `POST /api/sellers`; every answer is stored on `Store` (business, address, bank, operations, declarations) plus `applicationSignature` — the full name typed as an electronic signature (older app versions did not send it; keep it optional server-side). Multi-line text arrives with `\r\n` and is stored with `\n`.
- New applications notify every administrator (`store_application`, bell link `ADMIN_CONSOLE_URL/#stores`).
- Administrators read applications through `APPLICATION_SELECT` / `applicationView` (`src/lib/seller-application.ts`): the overview's `applications` (waiting ones) and `GET /api/admin/application?storeId=` (any store, with its logo/banner, ADMIN only). Never select the whole Store row for lists — it carries image data and encrypted processor keys.
- The admin console shows them in the Stores tab ("Read application" / "Application"), with Approve and Decline (+ a reason the seller is sent).

## Trust: verified sellers, real reviews, buyer protection

- **Verified seller** (`Store.verifiedAt`): set only by the admin action `store_verified` (console Stores tab, after checking the seller's identity and bank details); the seller is notified. Public store answers (`/api/sellers` slug, search, directory) and the product answer carry `verified`; the badge (`VerifiedSellerBadge`, `src/components/greengate/trust.tsx`) shows on store and product pages.
- **Items sold** on store answers: units on the store's orders in `SALE_STATUSES` (paid, not cancelled/returned/refunded).
- **Real reviews**: `POST /api/products/[id]/reviews` refuses (403) anyone without a paid order of that item; older unverified reviews stay visible without the badge.
- **Buyer protection**: the product-page box (`BuyerProtectionBox`) and Terms section `#buyer-protection` say only what is true (regulated providers, approved sellers, the legal rights in section 8, support@ steps in). Keep every statement true.
- **WhatsApp**: `WhatsAppShareLink` (wa.me) on product and store pages; the product page's link-preview image is the 640 px copy (`?w=640`).

## Pickup points (PAXI, Pudo) — `src/lib/pickup.ts`

- A seller offers collection at a PAXI point and/or a Pudo locker in the dashboard (`/api/seller/pickup`): their own price (R1–R1 000) and the delivery time they book. Suggested prices are the providers' published prices — never charged on their own.
- Checkout offers a pickup kind only when EVERY store in the cart offers it; `shippingCode` `paxi` / `pudo` charges each store its own price, needs no courier quote or doorstep pin, and stores the order's `address` as `PAXI point: <what the buyer typed>` with `shippingMethod` naming the kind and time. The seller sends the parcel there.

## Discount codes (seller-funded) — `src/lib/discounts.ts`

- Sellers create codes for their own store (`/api/seller/discounts`): % (1–90) or rand amount off their ITEMS (never delivery), optional minimum spend, first-order-only (buyer has no paid order on Green Gate), total uses, last day. Once per buyer. Up to 50 active per store.
- Buyers preview with `POST /api/discounts/check` (30 tries / 10 min per buyer); checkout re-checks every rule for every store before creating any order, claims the use INSIDE the order transaction (`claimDiscountUse` — the last use can never go to two buyers; the loser gets 409 "just used up"), and stores `discountCodeId` / `discountCode` / `discountCents`. **`totalCents = subtotalCents − discountCents + shippingCents`**; every payment rail charges `totalCents`.
- A store's items never cost less than R5 after a discount (`MIN_ITEMS_CENTS_AFTER_DISCOUNT`).
- Cancelling an order (`restockOrderItems`) gives the use back. The GGPay payout and seller analytics revenue are the items after the discount.
- Admin: the console's Discounts tab lists every code and can switch one off (`discount_code_admin`); the seller cannot switch it back on until Green Gate allows it.

## Photos by address, everywhere

Public and list answers send photos as `/api/images/<id>` addresses, never inline base64 (product detail, cart, wishlist, catalogue, recommendations; seller orders for live products via `firstPhotos` in `src/lib/item-photos.ts`). Only products no longer on sale keep an inline photo (their image route answers 404). Small slots ask for `?w=…` via `sizedImage`.

## Sellers never mark orders paid

- `confirm_payment` on `/api/seller/orders/[id]` is ADMIN-only and the "confirmed" status requires `paymentStatus === 'paid'` — payments confirm automatically through PayFast/Ozow/Yoco. The dashboard shows "Waiting for the buyer's payment" instead of the old EFT "Confirm payment received" button.

## Refund policy (owner's rule)

- **No refunds for change of mind — all sales are final** (Terms section 8, id `refund-policy`; `showRefundPolicy()` in legal-view.tsx opens it; shown at checkout under Place order, in the footer and the seller application). The statutory exceptions (CPA s56 faulty goods 6 months; wrong/undelivered items; ECTA s44 7-day cooling-off) MUST stay listed — South African law voids terms that remove them. Green Gate issues no refunds itself; the seller refunds through the original processor. See `docs/payments.md`.

## Search (stores + products)

- Header search → `#/?q=`. The storefront then shows a "Results for …" heading (no hero or recommendation rail, so results are visible first on phones), **matching stores** from `GET /api/sellers?q=` (active only, every word in name/description/location/slug, case-insensitive on Postgres) and products from `GET /api/products?q=`. Products: Algolia first; if its hits match no live product (stale index), the DB word search runs instead (`usedAlgolia && total === 0`). The Storefront is keyed by category+q, so each search remounts on page 1; the header box follows `route.q`. Offline: `OfflineBanner` (app-shell) tells the buyer while react-query pauses loads; they resume on reconnect. Test hostile environments with `qa/env-check.cjs` (slow 3G, dark, locales/time zones, offline) and every API with `qa/api-sweep.mjs` (`--live` = read-only). Test: `qa/search-check.cjs`.

## Delivery quotes (The Courier Guy)

- `/api/shipping` quotes PER STORE from each store's own location and sums each option exactly the way `/api/checkout` charges (same service per store, else that store's cheapest; rounded per order) — the delivery shown is the delivery charged. Response carries `sellerCount`.
- The checkout screen quotes only after typing pauses (700 ms, `quoteAddress` in cart-sheet.tsx) and always ticks an option that exists (`chosenShippingCode`). Per keystroke quoting used to send ~50 requests per address and hit the per-IP limit (now 90/min — carrier NAT). Test address entry with `pressSequentially`, never only `fill`.
- `tcgEta` picks the delivery-time sentence from TCG's description and skips booking/surcharge/contact notes (the live Same Day description starts with "kindly book your shipment before 14:00" and mentions an after-hours delivery surcharge — the buyer sees "Our standard turnaround time is 8-10 hours…").
- Collection booking (waybills) is NOT built: the owner must first choose seller-own vs marketplace Courier Guy account (`docs/delivery.md`).

## Real-money payment rails (how each one actually works — keep it this way)

- **PayFast** (marketplace account via `PAYFAST_*` env, or a seller's own account): signed form POSTed TOP-LEVEL to `https://www.payfast.co.za/eng/process` (sandbox host with `PAYFAST_SANDBOX=1`; `payfast.io/eng/process` 404s; PayFast must never be framed). Signature = md5 over fields in posting order, PHP-urlencoded (`payfastEncode`: spaces `+`, `!'()*~` escaped), passphrase appended. ITN: signature over fields IN THE ORDER RECEIVED (never sorted, empty values kept), merchant binding, `amount_gross` = order total, then PayFast's own confirmation (`payfastServerConfirms` → POST `/eng/query/validate` must answer `VALID`; unreachable → 500 so PayFast retries).
- **Ozow** (seller's own, Payments API): `POST https://api.ozow.com/postpaymentrequest` with `ApiKey` header, `hashCheck` in the JSON body; buyer is REDIRECTED to the returned `url` (Ozow's page may not be framed without its SDK). Notify hash order: SiteCode, TransactionId, TransactionReference, Amount, Status, Optional1–5, CurrencyCode, IsTest, StatusMessage + private key, lowercased, SHA-512. Site code must match the store; `IsTest=true` never pays a live order. Status: `GET /GetTransactionByReference`. Requires site code + private key + API key. (Ozow's One API — OAuth, for newly onboarded merchants — is NOT integrated yet.)
- **Yoco** (seller's own): live keys only on deployed builds (`yocoKeyUsable`) — a test key confirms orders paid with Yoco's public test cards while no money moves; refused when saving, at checkout, start, return and webhook.
- **Owner's rule — buyers pay ONLY through a processor the seller connected** (PayFast, Ozow, Yoco — or the marketplace PayFast account when configured), because those confirm instantly. Bank transfer (EFT) and pasted payment-page links are NOT buyer payment methods any more: `publicPaymentStore` always returns `eft: null`, `payoutLink: null`, `payoutNote: null`; order emails carry no bank details; the seller dashboard only offers PayFast/Ozow/Yoco/Mastercard. `storeTakesOnlinePayment(store)` (order-payment-options.ts) gates everything: `POST /api/cart` and `POST /api/checkout` answer 409 for a store without one, and product detail returns `canBuy: false` (the page shows "Not available to buy"). Seller bank details are still kept — for marketplace payouts only.
- **GGPay in-app card**: hidden + refused on every deployed build until a real acquirer is wired (fact 5).
- Order views only show a rail when `publicPaymentStore` says it is ready (same checks the payment routes enforce) — never a button that can only fail.
- Seller dashboard → Payment details shows a step-by-step setup guide for the chosen processor (`processor-setup-guide.tsx`) with copy buttons for this marketplace's real links (website, store page, notify/webhook URL, return pages — built from `window.location.origin`) and the processor dashboard paths (PayFast Settings → Developer Settings; Ozow Merchants → Merchant Details + Site page; Yoco Business Portal → Sell Online → Payment Gateway). Keep its facts in step with the integration.
- Seller dashboard → Payment details shows `paymentStatus` from `GET /api/sellers?mine=1` (`sellerPaymentStatus`): "Buyers can pay you with: …" plus plain warnings (PayFast without passphrase, Ozow without API key, Yoco test/unreadable key, chosen processor not connected, no bank details). `*KeySet` only means "something is saved". Saving: the PayFast passphrase is required; a passphrase or Ozow API key can be added on its own; re-saving without retyping a secret keeps the saved one.

## Older phones, smart TVs and every browser (Samsung, Hisense, …)

- `package.json` `browserslist` targets Chromium 69+ / Samsung Internet 10+ / Safari 12.1+ / Firefox 78+. Next.js 16 defaults to Chrome 111+, and its router code contained a class `static {}` block — a SyntaxError that stopped the whole app from starting on Chromium < 94 (older Samsung Internet, Android WebView, Samsung Tizen / Hisense VIDAA TV browsers). Never remove the browserslist; check with `npx es-check es2019 ".next/static/**/*.js"`.
- `src/app/layout.tsx` injects `LEGACY_POLYFILLS` (`next/script` beforeInteractive, ES5): globalThis, Promise.allSettled, AbortSignal.timeout, queueMicrotask. Next.js already polyfills Array.at, Object.hasOwn, flat, fromEntries…
- `postcss-legacy-compat.cjs` runs after Tailwind (imported in `postcss.config.mjs` — Turbopack cannot load a local plugin by string path). It unwraps `@layer` (Chromium < 99 ignored the whole stylesheet), gives every colour variable an `--x-rgb` triplet so `bg-x/15` tints fall back to a real see-through colour instead of solid (Chromium < 111), adds `transform` fallbacks for `translate/rotate/scale` (< 104, dialogs off-centre) and `top/right/bottom/left` before `inset` (< 87). Modern browsers render pixel-identically (verified: 20/20 screenshots, 0 px difference on Chrome, Safari, Firefox).
- `globals.css` keeps product photo boxes square without `aspect-ratio` (< 88).
- **Device lab** (`.github/workflows/device-lab.yml`, every push to main): builds the store, seeds a throwaway SQLite shop (`qa-lab/seed.mjs`) and drives it with OLD Chromium engines (Playwright Docker images 1.5–1.30 ≈ Chromium 87–110) using Samsung/Hisense phone and smart-TV profiles (`qa-lab/old-device-check.js`, ES2017): app starts, styles apply, photos visible, buyer signs in and reaches the seller's PayFast payment. A red run means older devices broke — fix before shipping.

## Sign-in that never strands a buyer

- Sessions last 30 days, renewed daily while used (`authOptions.session`). Shoppers were asked to sign in again after a week.
- `return-route.ts`: "Sign in" from checkout / orders / wishlist / Buy now remembers the page (sessionStorage); sign-in, registration and Google sign-in (app shell effect) return there. Before, every sign-in landed on the home page and buyers lost checkout.
- `session-guard.ts`: a session the server no longer accepts (expired in an open tab, password changed, incomplete) is signed out ONCE with "Please sign in again — your cart is kept", remembering the page. Triggered by the header's `/api/auth/me` check (query keyed by user id — a guest-time answer must never count) and by any query/mutation error "Sign in to continue" / "password was changed". Before, the header showed the buyer signed in while every purchase answered "Sign in to continue".

## Operations

- Security-sensitive rate limits (`rateLimitShared`) count in the project's Upstash Redis (`KV_REST_API_URL`/`KV_REST_API_TOKEN`) across all instances, falling back to the in-process limiter if Redis is missing/slow (1.5 s) — fallbacks are logged and the system monitor has a live "shared rate limiter (Redis)" check. Per-IP ceilings on register/reset/verify are generous (carrier NAT shares IPs); reset/verify also limit per email.
- Unpaid orders: warning 2 days before, then auto-cancel + restock after `UNPAID_ORDER_CANCEL_DAYS` (default 7; 0 = off) in `/api/cron/abandoned-checkouts` (atomic: a payment that lands first always wins). Restocking lives in `src/lib/inventory.ts` (also used by seller cancellations).
- Admin overview daily series is summed in SQL on Postgres (falls back to the row scan on any error).
- `/api/monitor` reuses its processor-adoption scan for 60 s (the console polls every second) and counts sellers as "ready" with the same checks checkout uses; when the database is down it answers 503 "Database unreachable" instead of a generic error.
- **The AI image SDK (`z-ai-web-dev-sdk`) only works where a `.z-ai-config` file exists (the original dev sandbox) — NOT on Vercel.** In production the AI-guard visual layer and the AI white-background pass are skipped; busy product photos get a white background via remove.bg (`REMOVE_BG_API_KEY` is set in production): photos whose outer ring is textured (`edgeRoughness` ≥ 3%) go to remove.bg BEFORE the flood fill (which can keep background objects on busy photos); remove.bg returns only the alpha matte, applied to the seller's full-size photo (`channels=alpha`, works at full resolution on free preview calls). Plain photos never call it. `REMOVE_BG_SIZE=preview` for tests. Counted as `remove_bg` in API usage; `/api/health` reports "photo backgrounds". Test with `qa/removebg-check.mjs`.
- **sharp is loaded lazily** (`src/lib/sharp-loader.ts`). Never `import sharp from 'sharp'` at the top of a module: a missing native binary then fails every route importing it (it took down GET /api/products and /api/sellers in a local standalone build). Outbound AI calls (photo guard 60 s, white-background 45 s) have hard timeouts.
- Local standalone builds on Windows miss sharp's DLLs (`node_modules/@img/sharp-win32-x64/lib/*.dll`) — copy them into `.next/standalone/node_modules/@img/sharp-win32-x64/lib/` for local testing. Vercel (Linux) is unaffected.
- Vercel: Preview deployments are protected (Vercel Authentication) and do NOT receive database credentials or secrets (Production keeps all 68 vars) — previews run on ephemeral SQLite. Do not re-add production secrets to Preview.
- Product cards link the name to `/product/<slug>` (crawlable); a plain click is intercepted for in-app hash navigation. The product view's Share button shares the `/product/<slug>` URL.
- Store applications start `pending` — products require an `active` store (admin approves, or activate directly in the local DB for tests).
- Registering accounts is rate-limited (5/h/IP) — reuse fixed identities for re-runs.
- The admin console's own login route is rate-limited separately (10/5min).
